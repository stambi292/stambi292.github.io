Process mining · purchase-to-pay · real event log

One process, 11,963 paths

On paper, buying works in five steps: order, receive, get the invoice, record it, pay. I mined 1.6 million real events from a multinational's purchasing system to see what actually happens, where invoices get stuck, and what fixing it is worth.

Independent analysis by Stephen tAMBI on a public, anonymised event log (BPI Challenge 2019). Not affiliated with the company or any software vendor.

How it was built

  • Data:
  • Process mining: each purchase order item is one case. Its events, in time order, form its path (variant). Waiting times are medians between the first occurrence of each step.
  • Groups: "payment block" = items with a "Remove Payment Block" step; "rework" = items with a change, cancellation, deletion or block step; "clean" = neither.
  • Tools: Python with pandas and lxml to parse the XES log and compute paths, waiting times and rework. Event values in the log are skewed by a few very large items, so the page uses counts and medians.
Data: BPI Challenge 2019, van Dongen, B.F., 4TU.ResearchData, event log of the purchase-to-pay process of a large multinational in coatings and paints, operating from the Netherlands.
